# 朝代差异化边界：共享「交互语法/能力」，朝代各自是「迥然不同的沉浸世界」（B+），以「穿越转场」连接

「每个朝代独立视觉」是项目灵魂。访谈中用户进一步明确愿景：**每个朝代应是一个迥然不同的沉浸世界**，通过一扇「时间旅行之门」穿越进入（例：宋朝＝俯瞰《清明上河图》、栩栩如生、人来人往，随即「抵达」宋朝世界，整体风格也变为宋）。

关键澄清：**「视觉迥然不同」属于「表达」，不等于「架构各自从零(C)」。** 决策为 **B+**——共享层划在「看不见的能力/交互语法」，而非「看得见的长相/布局」：

- **平台共享（看不见的能力）**：滚动引擎、**穿越转场系统**、内容原子与数据层、关系图谱机制、详情抽屉机制、交互语法（怎么点/怎么深潜）、无障碍与性能基线。
- **朝代独立（看得见的世界，迥然不同）**：专属沉浸 Hero / 穿越门户、背景氛围、配色/字体/纹样/留白节奏、分区结构与布局、组件长相、关系图谱的视觉风格、招牌场景。

## Considered Options

- **A · 统一房子换配色/字体**：否决，「独立视觉」太弱。
- **C · 真·每朝代完全独立**（导航/滚动/组件/交互各自从零）：否决——给出**相同的视觉效果**，却带来：每朝代≈一个新项目、用户每进一朝需重学操作（违背「不要让用户思考」）、穿越转场失去统一框架沦为拼凑、维护成本爆炸。**用户的「穿越转场」愿景本身要求一个共享的穿越机制，反而为共享平台投票。**
- **B+ · 共享能力 + 朝代独立世界 + 穿越转场**：✅ 选中。迥然不同的世界，但交互语法一致、新朝代可建、穿越连贯。

## Consequences

- **架构第一刀**：接通断掉的主题管线，让朝代主题（配色/字体/纹样/氛围）真正驱动其世界呈现；并新建两个平台能力——**穿越转场系统** 与 **关系图谱原语**。
- platform/dynasty 边界据此明确：**能力下沉平台、世界上浮朝代**。新增朝代 ＝ 数据 + 主题 + 沉浸世界(Hero/门户/背景) + 分区叙事 + 招牌场景 + 关系图谱布局，**不重写平台**。
- 「穿越转场」是一等体验：进/出每个朝代世界都经由它，需作为平台级机制设计（含 reduced-motion 降级）。
- 平台层现存的明朝特定渗入（footer 文案、CATEGORY_LABELS、RELATION_LEGEND 等）需「去明朝化」或下放朝代层。
- 清明上河图类「世界门户」按 **编辑级电影感** 实现（GSAP 在真实画作上平移/推拉/视差 + 微动），守住 ADR-0001 温度 A；若改为活体模拟则需重开 ADR-0001。
